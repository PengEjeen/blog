HLS 기반 영상 스트리밍 서비스를 제공하다가 문제가 생겼다..

영상 스트리밍 서비스에서는 동일한 콘텐츠에 대해 다수 사용자가 동시에 요청을 보내는 상황이 빈번하게 발생한다. 이 경우 모든 요청을 원본 서버(Origin)에서 직접 처리하면 트래픽이 집중되면서 네트워크 대역폭 사용량이 급격히 증가하고, 지연(latency)과 서버 부하가 함께 악화된다.
이를 해결하기 위해 CDN(Content Delivery Network)을 사용하였다.

## 1. CDN(Content Delivery Network)
# 1.1 CDN이란?
  콘텐츠 전송 네트워크 CDN(Content Delivery Network)은 데이터 사용량이 많은 애플리케이션의 웹 페이지 로드 속도를 높이는 상호 연결된 서버 네트워크이다. CDN은 콘텐츠 전송 네트워크 또는 콘텐츠 배포 네트워크를 의미할 수 있다. 사용자가 웹 사이트를 방문할 때 해당 웹 사이트 서버의 데이터는 사용자의 컴퓨터에 도달하기 위해 인터넷을 통해 이동해야 한다. 사용자가 해당 서버에서 멀리 떨어져 있는 경우 동영상 또는 웹 사이트 이미지와 같은 대용량 파일을 로드하는 데 시간이 오래 걸린다. 대신 웹 사이트 콘텐츠는 지리적으로 사용자와 가까운 CDN 서버에 저장되면 컴퓨터에 훨씬 빨리 도달하게 된다.

# 1.2 CDN 사용 시의 이점

**페이지 로드 시간 단축**
페이지 로드 시간이 너무 느리면 웹 사이트 트래픽이 감소 할 수 있음. CDN은 반송률을 줄이고 사용자가 사이트에서 보내는 시간을 늘릴 수 있음.

**대역폭 비용 절감**
들어오는 모든 웹 사이트 요청은 네트워크 대역폭을 사용하기 때문에 대역폭 비용이 상당히 높다. 캐싱 및 기타 최적화를 통해 CDN은 오리진 서버가 제공해야 하는 데이터의 양을 줄여 웹 사이트 소유자의 호스팅 비용을 절감할 수 있다.

**콘텐츠 가용성 제고**
한 번에 너무 많은 방문자가 방문하거나 네트워크 하드웨어 오류가 발생하면 웹 사이트가 중단될 수 있다. CDN 서비스는 더 많은 웹 트래픽을 처리하고 웹 서버의 로드를 줄일 수 있다. 또한 하나 이상의 CDN 서버가 오프라인으로 전환되면 다른 운영 서버가 해당 서버를 대체하여 서비스가 중단되자 않도록 할 수 있다.

**웹 사이트 보안 강화**
DDoS 공격은 대량의 가짜 트래픽을 웹 사이트로 전송하여 애플리케이션이 작동 중지되도록 만들려고 시도한다. CDN은 여러 중간 서버 간에 로드를 분산하여 오리진 서버에 미치는 영향을 줄임으로써 이러한 트래픽 급증을 처리할 수 있다.

# 1.3 CDN 작동 방식
CDN은 정적 콘텐츠와 동적 콘텐츠의 두 가지 유형의 콘텐츠 전송 가능하다.

**정적 콘텐츠**
정적 콘텐츠는 사용자 간에 변경되지 않는 웹 사이트 데이터다. 이미지, 동영상, CSS 파일, JavaScript 번들, HLS 세그먼트(.ts) 파일처럼 한 번 만들어지면 거의 바뀌지 않는 자원이 여기에 해당한다. 정적 콘텐츠는 캐싱하기 쉬워 CDN이 가장 잘 활용되는 영역이다.

**동적 콘텐츠**
동적 콘텐츠는 사용자, 위치, 시간 등에 따라 다르게 생성되는 데이터다. 로그인 후의 개인화 페이지, 실시간 추천 결과, 결제 응답 등이 해당한다. 동적 콘텐츠는 매번 오리진에서 새로 생성되는 경우가 많지만, 최근 CDN은 엣지 컴퓨팅(Edge Compute)이나 동적 라우팅 최적화를 통해 동적 콘텐츠 전달 성능도 함께 끌어올리고 있다.

**전체 흐름**
CDN은 전 세계에 분산된 엣지 서버(Edge Server, PoP)에 콘텐츠 사본을 보관한다. 사용자가 콘텐츠를 요청하면 DNS는 가장 가까운 엣지 서버로 트래픽을 라우팅하고, 엣지 서버는 다음 순서로 응답한다.

1. **Cache HIT**: 엣지에 캐시된 사본이 있으면 즉시 응답한다. 오리진까지 갈 필요가 없어 가장 빠르다.
2. **Cache MISS**: 캐시가 없으면 오리진(또는 상위 캐시 계층)에서 콘텐츠를 가져온 뒤, 응답을 사용자에게 전달하면서 동시에 엣지에 저장한다. 이후 같은 요청은 HIT로 처리된다.
3. **TTL 만료**: 캐시는 `Cache-Control`, `Expires` 헤더 기반의 TTL을 가지며, 만료 시 오리진에 재검증(revalidate)하거나 새로 가져온다.

이 구조 덕분에 오리진 서버는 "최초 1회 + 캐시 만료 시"에만 트래픽을 처리하면 되고, 나머지 대다수 요청은 사용자와 가까운 엣지에서 흡수된다.

## 2. HLS 스트리밍과 CDN

HLS(HTTP Live Streaming)는 영상을 짧은 세그먼트(.ts) 단위로 잘라 두고, 플레이리스트(.m3u8)에 그 목록을 적어 클라이언트가 순차적으로 받아 재생하는 방식이다. 모든 통신이 일반 HTTP 요청으로 이루어지기 때문에 CDN과 매우 잘 맞는다.

# 2.1 HLS 파일의 캐싱 특성

| 파일 | 변경 빈도 | 캐싱 전략 |
| --- | --- | --- |
| `.ts` 세그먼트 | 인코딩 완료 후 거의 불변 | **장기 캐싱** (예: `max-age=31536000`, immutable) |
| `.m3u8` (VOD) | 거의 불변 | 중기 캐싱 |
| `.m3u8` (Live) | 수 초마다 갱신 | **짧은 TTL** (예: 1~5초) 또는 캐시 우회 |
| 키 파일(.key) | 권한별 다름 | 캐시 금지 또는 서명 URL |

특히 `.ts` 세그먼트는 한 번 생성되면 내용이 변하지 않으므로, 적극적으로 엣지에 캐싱해도 안전하다. 반면 라이브 스트리밍의 `.m3u8`은 새 세그먼트가 추가될 때마다 갱신되어야 하므로, TTL을 짧게 잡거나 별도의 캐시 키를 설계해야 한다.

# 2.2 왜 CDN이 필요했는가

같은 영상에 다수의 시청자가 몰리는 상황을 떠올려 보자. CDN이 없다면 모든 `.m3u8` 요청과 수많은 `.ts` 세그먼트 요청이 그대로 오리진에 도달한다. 영상 비트레이트가 높을수록 한 명당 발생하는 트래픽이 커지고, 동시 시청자 수에 비례해 대역폭 비용과 부하가 선형 이상으로 증가한다.

CDN을 끼우면 다음이 달라진다.

- **오리진 트래픽 평탄화**: 동일 세그먼트에 대한 N개의 요청이 엣지에서 1번의 오리진 요청으로 합쳐진다(Origin Shielding을 두면 더 강해진다).
- **지연 감소**: 시청자와 물리적으로 가까운 엣지에서 응답하므로 첫 프레임 도달 시간(Time-to-First-Frame)과 버퍼링이 줄어든다.
- **장애 격리**: 일부 엣지가 죽어도 다른 엣지가 같은 콘텐츠를 서빙할 수 있다.

## 3. 적용하면서 고민했던 것들

# 3.1 캐시 키 설계

처음에는 단순히 URL만으로 캐시 키를 잡았는데, 같은 영상이라도 토큰이 쿼리스트링에 붙으면서 캐시가 사용자마다 따로 생성되는 문제가 있었다. 이 경우 캐시 HIT율이 거의 0에 수렴한다.

해결책은 두 가지였다.

- 권한 검증에 사용하는 쿼리 파라미터를 **캐시 키에서 제외**한다.
- 또는 권한 검증을 **엣지에서 처리**(서명 URL, 토큰 검증)하고, 오리진까지 갈 필요가 없게 한다.

# 3.2 Cache-Control 헤더

오리진에서 응답할 때 헤더를 명확하게 지정하지 않으면 CDN마다 기본값이 달라 의도와 다르게 동작한다. `.ts`에는 길고 강한 캐시를, `.m3u8`(라이브)에는 매우 짧은 TTL을 주는 식으로 콘텐츠별로 따로 설정했다.

```http
# .ts segment
Cache-Control: public, max-age=31536000, immutable

# live .m3u8
Cache-Control: public, max-age=2, s-maxage=2
```

# 3.3 오리진 보호

CDN을 거치지 않고 오리진을 직접 때리는 트래픽이 있으면 CDN의 의미가 절반쯤 사라진다. 오리진 측에서는 CDN의 IP 대역만 허용하거나, 공유 시크릿 헤더를 검증해 직격 트래픽을 차단했다.

# 3.4 캐시 무효화(Invalidation)

영상이 교체되거나 권한이 회수되는 시점에는 엣지 캐시도 함께 비워야 한다. 그렇지 않으면 새 정책이 적용되기까지 TTL이 만료될 때까지 기다려야 한다. 무효화는 비용과 전파 시간이 있으므로 너무 자주 일으키지 않도록, 파일 경로에 버전 토큰을 포함하는 방식(`/v2/...`)으로 자연 무효화를 유도하는 편이 안전했다.

## 4. 마무리

요약하면, CDN은 "오리진과 사용자 사이에 거대한 캐시 계층을 끼우는" 단순한 아이디어이지만, HLS처럼 작은 파일이 대량으로 오가는 워크로드에서는 비용과 품질을 동시에 살려주는 핵심 인프라였다. 도입 자체는 어렵지 않았지만, 캐시 키·헤더·무효화·오리진 보호 네 가지를 제대로 설계하지 않으면 "분명히 CDN을 깔았는데 왜 비용이 줄지 않지?" 하는 상황이 쉽게 생긴다.

다음에 비슷한 스트리밍 시스템을 다시 구성한다면, 처음부터 **캐시 키 정책과 헤더 규칙을 문서로 먼저 정한 뒤** 인프라를 깔 것 같다.
