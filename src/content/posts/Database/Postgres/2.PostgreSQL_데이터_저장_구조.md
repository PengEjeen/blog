# 2. PostgreSQL 데이터 저장 구조

> **TL;DR**: PostgreSQL의 일반 테이블은 Heap 형태로 저장된다. 테이블 파일은 보통 8KB 크기의 Page로 나뉘며, 각 Page 안에는 실제 행인 Tuple이 들어간다. `UPDATE`는 기존 Tuple을 덮어쓰지 않고 새 버전을 만들기 때문에 MVCC가 가능하지만, 사용이 끝난 Tuple을 정리하는 Vacuum도 필요하다.

## 2.1 이 구조를 왜 알아야 할까?

애플리케이션에서는 테이블을 행과 열의 집합으로 바라본다.

```sql
SELECT id, name
FROM members
WHERE id = 1;
```

하지만 PostgreSQL은 테이블을 하나의 거대한 표로 저장하지 않는다. 실제 데이터는 파일, Page, Tuple이라는 여러 단계를 거쳐 저장된다.

```text
Database Cluster
└── Database
    └── Relation File
        └── Page
            └── Tuple
```

이 구조를 알면 다음과 같은 질문에 답하기 쉬워진다.

- 행을 수정했는데 테이블 크기가 커지는 이유는 무엇일까?
- `DELETE`한 공간이 운영체제에 바로 반환되지 않는 이유는 무엇일까?
- 인덱스가 있어도 Heap을 다시 읽는 경우가 있는 이유는 무엇일까?
- 큰 `TEXT`나 `JSONB` 값은 한 Page에 어떻게 저장될까?
- Vacuum과 HOT Update는 성능에 어떤 영향을 줄까?

이번 장에서는 PostgreSQL이 데이터를 저장하는 단위를 살펴보고, 직접 Tuple의 위치와 버전 정보를 확인한다.

## 2.2 실습 환경 준비

1장에서 만든 PostgreSQL 18 컨테이너를 사용한다.

```bash
docker start postgres-local
```

컨테이너가 없다면 새로 실행한다.

```bash
docker run \
  --name postgres-local \
  -e POSTGRES_PASSWORD=postgres \
  -p 5432:5432 \
  -d postgres:18
```

`psql`로 접속한다.

```bash
docker exec -it postgres-local \
  psql -U postgres -d postgres
```

Page 내부를 확인할 때 사용할 `pageinspect` 확장을 활성화한다.

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;
```

`pageinspect`는 데이터 Page의 원시 내용을 확인하는 저수준 도구다. 운영 데이터베이스에서 무분별하게 사용하기보다 학습이나 문제 분석 목적으로 제한해서 사용하는 편이 안전하다.

## 2.3 논리 구조와 물리 구조

PostgreSQL에는 사용자가 SQL에서 다루는 논리 구조와 디스크에 저장되는 물리 구조가 있다.

### 2.3.1 논리 구조

논리 구조는 다음과 같이 표현할 수 있다.

```text
Database Cluster
├── Database
│   ├── Schema
│   │   ├── Table
│   │   ├── Index
│   │   ├── View
│   │   └── Sequence
│   └── ...
└── ...
```

하나의 PostgreSQL 서버 인스턴스가 관리하는 전체 데이터 집합을 Database Cluster라고 한다. 하나의 Cluster에는 여러 Database가 있고, 각 Database 안에는 Schema와 Table 같은 객체가 존재한다.

서로 다른 Database의 객체를 일반 SQL에서 바로 조인할 수는 없다. 반면 Schema는 하나의 Database 안에서 객체의 이름을 구분하는 Namespace 역할을 한다.

### 2.3.2 물리 구조

테이블과 인덱스는 PostgreSQL에서 Relation으로 취급되며, 기본적으로 각각 별도의 파일에 저장된다.

```text
PGDATA
└── base
    └── 데이터베이스 OID
        ├── 테이블의 filenode
        ├── 테이블의 filenode_fsm
        ├── 테이블의 filenode_vm
        └── ...
```

테이블 파일이 기본 설정에서 1GB보다 커지면 하나의 파일을 계속 키우는 대신 여러 Segment로 나눈다.

```text
16390
16390.1
16390.2
```

파일명에 사용되는 filenode는 테이블의 논리적 식별자인 OID와 항상 같지는 않다. `TRUNCATE`, `REINDEX`, `CLUSTER`와 일부 `ALTER TABLE` 작업은 객체의 OID를 유지하면서 filenode를 바꿀 수 있다.

테이블 파일의 상대 경로는 다음 함수로 확인한다.

```sql
SELECT pg_relation_filepath('members');
```

크기도 함께 확인해 볼 수 있다.

```sql
SELECT
    pg_size_pretty(pg_relation_size('members')) AS table_size,
    pg_size_pretty(pg_indexes_size('members')) AS indexes_size,
    pg_size_pretty(pg_total_relation_size('members')) AS total_size;
```

`pg_relation_size()`는 지정한 Relation의 크기를 반환한다. `pg_total_relation_size()`는 테이블 본체뿐 아니라 인덱스와 TOAST 데이터까지 포함한 전체 크기를 반환한다.

## 2.4 Heap, Page, Tuple

PostgreSQL의 기본 테이블 접근 방식은 Heap이다.

여기서 Heap은 자료구조에서 말하는 우선순위 큐가 아니다. 행이 특정 키 순서대로 저장된다고 보장하지 않는 테이블 저장 방식을 의미한다.

```text
Heap Relation
├── Page 0
│   ├── Tuple 1
│   ├── Tuple 2
│   └── Tuple 3
├── Page 1
│   ├── Tuple 1
│   └── Tuple 2
└── Page 2
    └── ...
```

각 용어의 의미는 다음과 같다.

| 용어 | 의미 |
| --- | --- |
| Relation | 테이블이나 인덱스처럼 PostgreSQL이 관리하는 객체 |
| Heap | 일반 테이블에서 사용하는 기본 저장 방식 |
| Page 또는 Block | Relation 파일을 읽고 쓰는 기본 단위 |
| Tuple | Page 안에 저장되는 하나의 행 버전 |
| Item Identifier | Page 안에서 Tuple의 위치를 가리키는 항목 |

PostgreSQL의 Page 크기는 일반적으로 8KB다. 컴파일 시 다른 크기를 선택할 수 있지만, 하나의 실행 중인 Cluster 안에서는 동일한 Page 크기를 사용한다.

현재 서버의 Block 크기는 다음 명령으로 확인할 수 있다.

```sql
SHOW block_size;
```

기본 환경에서는 다음 값이 나온다.

```text
 block_size
------------
 8192
```

## 2.5 Page 내부 구조

일반적인 Page는 크게 다섯 영역으로 나뉜다.

```text
낮은 주소
┌──────────────────────────────┐
│ Page Header                  │
├──────────────────────────────┤
│ Item Identifier 1            │
│ Item Identifier 2            │
│ Item Identifier 3            │
├──────────────────────────────┤
│                              │
│ Free Space                   │
│                              │
├──────────────────────────────┤
│ Tuple 3                      │
│ Tuple 2                      │
│ Tuple 1                      │
├──────────────────────────────┤
│ Special Space                │
└──────────────────────────────┘
높은 주소
```

### 2.5.1 Page Header

Page의 앞부분에는 24바이트 크기의 Header가 있다. Header에는 다음과 같은 정보가 기록된다.

- 이 Page의 마지막 변경과 관련된 WAL 위치
- Page Checksum
- Item Identifier 영역의 끝 위치
- Tuple 데이터가 시작되는 위치
- 특수 영역이 시작되는 위치
- 정리가 필요한 오래된 Tuple에 대한 힌트

Header의 `pd_lower`와 `pd_upper` 사이가 아직 사용하지 않은 공간이다. 새 Item Identifier는 앞쪽에서 뒤쪽으로 늘어나고, 새 Tuple은 뒤쪽에서 앞쪽으로 쌓인다.

### 2.5.2 Item Identifier

Item Identifier는 실제 Tuple의 위치와 길이를 저장한다. 하나의 Item Identifier는 4바이트를 사용한다.

PostgreSQL은 Page 안에서 Tuple을 정리하거나 이동할 수 있지만, 가능한 한 Item Identifier의 번호는 안정적으로 유지한다. 따라서 다른 객체에서는 Tuple의 실제 바이트 위치가 아니라 Page 번호와 Item Identifier 번호의 조합으로 행을 가리킨다.

### 2.5.3 Tuple

Tuple은 사용자가 입력한 열 데이터만 가지고 있지 않다. PostgreSQL이 행 버전의 가시성을 판단하기 위한 Header도 포함한다.

대표적인 Tuple Header 정보는 다음과 같다.

| 필드 | 역할 |
| --- | --- |
| `xmin` | 이 Tuple을 생성한 트랜잭션 ID |
| `xmax` | 이 Tuple을 삭제했거나 새 버전으로 교체한 트랜잭션 ID |
| `ctid` | 현재 Tuple 또는 다음 Tuple 버전의 물리적 위치 |
| `infomask` | Tuple 상태를 나타내는 여러 Flag |

이 정보 덕분에 PostgreSQL은 같은 행의 여러 버전 중 현재 트랜잭션에 보여야 할 버전을 선택할 수 있다.

## 2.6 `ctid`, `xmin`, `xmax` 확인하기

실습용 테이블을 생성한다.

```sql
DROP TABLE IF EXISTS members;

CREATE TABLE members (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    point INTEGER NOT NULL DEFAULT 0
);
```

행을 세 개 추가한다.

```sql
INSERT INTO members (name, point)
VALUES
    ('kim', 100),
    ('lee', 200),
    ('park', 300);
```

일반 열과 함께 PostgreSQL의 시스템 열을 조회한다.

```sql
SELECT ctid, xmin, xmax, id, name, point
FROM members
ORDER BY id;
```

결과는 환경마다 다르지만 다음과 비슷하다.

```text
 ctid  | xmin | xmax | id | name | point
-------+------+------+----+------+-------
 (0,1) |  740 |    0 |  1 | kim  |   100
 (0,2) |  740 |    0 |  2 | lee  |   200
 (0,3) |  740 |    0 |  3 | park |   300
```

`ctid`의 첫 번째 숫자는 Page 번호이고 두 번째 숫자는 Page 안의 Item Identifier 번호다.

```text
(0, 1)
 │  └── Page 안의 Item Identifier 번호
 └───── Page 번호
```

세 행이 모두 `(0, n)` 형태인 것은 현재 데이터가 첫 번째 Page에 들어갔기 때문이다.

`xmin`은 각 Tuple을 만든 트랜잭션 ID다. 하나의 `INSERT` 문으로 세 행을 추가했으므로 같은 `xmin`을 가진다. `xmax`가 0이라는 것은 아직 다른 트랜잭션에 의해 삭제되거나 교체된 상태가 아니라는 뜻이다.

> `ctid`는 물리적 위치이므로 `UPDATE`, `VACUUM FULL` 등의 작업으로 바뀔 수 있다. 애플리케이션의 기본 키로 사용하면 안 된다.

## 2.7 UPDATE는 행을 덮어쓰지 않는다

`id = 1`인 회원의 Point를 변경한다.

```sql
UPDATE members
SET point = 150
WHERE id = 1;
```

다시 조회한다.

```sql
SELECT ctid, xmin, xmax, id, name, point
FROM members
ORDER BY id;
```

다음과 같이 첫 번째 행의 `ctid`와 `xmin`이 바뀐 것을 확인할 수 있다.

```text
 ctid  | xmin | xmax | id | name | point
-------+------+------+----+------+-------
 (0,4) |  741 |    0 |  1 | kim  |   150
 (0,2) |  740 |    0 |  2 | lee  |   200
 (0,3) |  740 |    0 |  3 | park |   300
```

논리적으로는 하나의 행을 수정했지만, 물리적으로는 새 Tuple `(0,4)`가 생성됐다.

```text
UPDATE 이전
(0,1) kim, 100

UPDATE 이후
(0,1) kim, 100  ← 이전 Tuple
(0,4) kim, 150  ← 새 Tuple
```

일반 `SELECT`에는 현재 트랜잭션에서 볼 수 있는 새 버전만 나타난다. 이전 버전은 다른 트랜잭션의 Snapshot에 필요할 수 있으므로 즉시 제거되지 않는다.

`pageinspect`를 사용하면 일반 조회에서 보이지 않는 Tuple도 Page 수준에서 살펴볼 수 있다.

```sql
SELECT
    lp,
    t_xmin,
    t_xmax,
    t_ctid
FROM heap_page_items(get_raw_page('members', 0))
ORDER BY lp;
```

예상 결과는 다음과 비슷하다.

```text
 lp | t_xmin | t_xmax | t_ctid
----+--------+--------+--------
  1 |    740 |    741 | (0,4)
  2 |    740 |      0 | (0,2)
  3 |    740 |      0 | (0,3)
  4 |    741 |      0 | (0,4)
```

이전 Tuple `(0,1)`의 `xmax`에는 이를 교체한 트랜잭션 ID가 기록되고, `t_ctid`는 새 Tuple `(0,4)`를 가리킨다.

이처럼 행 버전을 새로 만드는 방식이 PostgreSQL MVCC의 기반이다. 각 트랜잭션은 자신의 Snapshot과 Tuple Header를 비교해 어떤 버전을 볼 수 있는지 판단한다.

## 2.8 HOT Update

PostgreSQL의 인덱스는 일반적으로 Heap Tuple의 위치를 가리킨다.

```text
Index Entry
    │
    ▼
Heap Tuple의 ctid
```

행을 수정할 때마다 모든 인덱스에 새 항목을 추가한다면 쓰기 비용과 인덱스 크기가 빠르게 증가할 수 있다. PostgreSQL은 조건이 맞으면 HOT(Heap-Only Tuple) Update를 사용해 불필요한 인덱스 갱신을 줄인다.

HOT Update가 가능한 대표적인 조건은 다음과 같다.

- 인덱스가 참조하는 열을 변경하지 않았다.
- 같은 Page에 새 Tuple을 저장할 여유 공간이 있다.

앞의 예제에서 `point`에 인덱스가 없고 새 Tuple도 같은 Page에 저장됐다면 HOT Update가 사용될 수 있다.

```text
Index
  │
  ▼
이전 Heap Tuple ── HOT Chain ──▶ 새 Heap Tuple
```

HOT Update가 발생하면 기존 인덱스 항목을 통해 같은 Page 안의 최신 Tuple을 찾을 수 있다. 실제 발생 횟수는 통계 View에서 확인한다.

```sql
SELECT
    relname,
    n_tup_upd,
    n_tup_hot_upd
FROM pg_stat_user_tables
WHERE relname = 'members';
```

통계는 비동기적으로 반영될 수 있으므로 `UPDATE` 직후 같은 세션에서 조회하면 값이 바로 보이지 않을 수 있다.

자주 수정되는 테이블에서는 `fillfactor`를 낮춰 Page 안에 여유 공간을 남기는 방법도 있다.

```sql
ALTER TABLE members SET (fillfactor = 80);
```

`fillfactor = 80`은 새 데이터를 채울 때 Page의 약 20%를 이후 UPDATE를 위한 공간으로 남기도록 유도한다. HOT Update 가능성을 높일 수 있지만, 같은 데이터가 더 많은 Page를 사용하게 되므로 읽기 비용과 저장 공간도 함께 고려해야 한다.

## 2.9 Free Space Map과 Visibility Map

테이블에는 본체인 Main Fork 외에도 공간과 가시성 정보를 관리하는 별도 Fork가 존재할 수 있다.

```text
Relation
├── main : 실제 Page와 Tuple
├── fsm  : Page별 여유 공간 정보
└── vm   : Page별 가시성 정보
```

### 2.9.1 Free Space Map

Free Space Map(FSM)은 각 Page에 어느 정도의 빈 공간이 있는지 기록한다.

새 Tuple을 저장할 때 모든 Page를 처음부터 읽어 빈 공간을 찾는 것은 비효율적이다. PostgreSQL은 FSM을 참고해 새 Tuple이 들어갈 가능성이 있는 Page를 선택한다.

FSM은 정확한 빈 공간의 바이트 수 전체를 저장하기보다 제한된 크기의 값으로 근사해 관리한다. 따라서 FSM이 알려 준 Page에 실제 Tuple을 저장할 공간이 부족하면 다른 Page를 다시 찾을 수도 있다.

### 2.9.2 Visibility Map

Visibility Map(VM)은 Heap Page마다 다음 두 상태를 기록한다.

| 상태 | 의미 |
| --- | --- |
| all-visible | Page의 모든 Tuple이 현재와 미래의 모든 트랜잭션에 보이는 상태 |
| all-frozen | Page의 모든 Tuple이 Transaction ID Wraparound 보호를 위해 Freeze된 상태 |

데이터를 변경하면 관련 Page의 Visibility 상태가 해제될 수 있고, Vacuum이 Page를 확인한 뒤 다시 설정한다.

Visibility Map은 Vacuum이 이미 안전한 Page를 건너뛸 수 있게 도와준다. 또한 Index-Only Scan을 수행할 때 Heap Page를 다시 읽지 않아도 되는지 판단하는 데 사용된다.

```text
일반 Index Scan
Index → Heap Page → Tuple 확인

Index-Only Scan
Index + Visibility Map → 결과 반환 가능
```

이름과 달리 Index-Only Scan이 항상 인덱스만 읽는 것은 아니다. Visibility Map에서 Page가 all-visible이라고 확인돼야 Heap 접근을 생략할 수 있다.

## 2.10 큰 값은 TOAST에 저장한다

일반적인 Page 크기는 8KB이므로 매우 긴 `TEXT`나 큰 `JSONB` 값을 행 안에 그대로 저장하기 어렵다.

PostgreSQL은 TOAST(The Oversized-Attribute Storage Technique)를 사용해 큰 가변 길이 값을 압축하거나 별도의 TOAST Table로 분리한다.

```text
Heap Tuple
├── id
├── title
└── body의 TOAST Pointer
             │
             ▼
       TOAST Table
       ├── Chunk 1
       ├── Chunk 2
       └── Chunk 3
```

실습용 테이블을 만든다.

```sql
DROP TABLE IF EXISTS documents;

CREATE TABLE documents (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL,
    body TEXT NOT NULL
);
```

큰 문자열을 추가한다.

```sql
INSERT INTO documents (title, body)
VALUES (
    'PostgreSQL Storage',
    repeat(md5(random()::text), 10000)
);
```

논리적인 값의 길이와 실제 저장에 사용되는 크기를 비교한다.

```sql
SELECT
    id,
    octet_length(body) AS logical_bytes,
    pg_column_size(body) AS stored_bytes
FROM documents;
```

TOAST Table의 존재 여부는 `pg_class`에서 확인할 수 있다.

```sql
SELECT
    relname AS table_name,
    reltoastrelid::regclass AS toast_table
FROM pg_class
WHERE oid = 'documents'::regclass;
```

전체 Relation 크기도 확인한다.

```sql
SELECT
    pg_size_pretty(pg_relation_size('documents')) AS main_size,
    pg_size_pretty(pg_total_relation_size('documents')) AS total_size;
```

PostgreSQL은 값의 크기와 열의 Storage 전략에 따라 압축과 외부 저장 여부를 결정한다.

| Storage 전략 | 동작 |
| --- | --- |
| `PLAIN` | 압축과 외부 저장을 허용하지 않는다. |
| `EXTENDED` | 압축과 외부 저장을 모두 허용한다. |
| `EXTERNAL` | 압축하지 않고 외부 저장을 허용한다. |
| `MAIN` | 압축을 우선하며 외부 저장은 가능한 한 피한다. |

열의 현재 전략은 다음과 같이 확인할 수 있다.

```sql
SELECT
    attname,
    CASE attstorage
        WHEN 'p' THEN 'PLAIN'
        WHEN 'e' THEN 'EXTERNAL'
        WHEN 'm' THEN 'MAIN'
        WHEN 'x' THEN 'EXTENDED'
    END AS storage
FROM pg_attribute
WHERE attrelid = 'documents'::regclass
  AND attnum > 0
  AND NOT attisdropped;
```

일반적인 `TEXT` 열은 `EXTENDED` 전략을 사용한다. 직접 전략을 변경할 수도 있지만, 조회 방식과 저장 공간에 미치는 영향을 이해하지 않은 상태에서 기본값을 바꿀 필요는 없다.

## 2.11 DELETE 이후 파일 크기가 바로 줄지 않는 이유

행을 삭제해 보자.

```sql
DELETE FROM members
WHERE id = 2;
```

PostgreSQL은 다른 트랜잭션이 이전 Snapshot을 통해 해당 행을 볼 가능성이 있으므로 Tuple을 즉시 물리적으로 제거하지 않는다. 우선 삭제한 트랜잭션 정보를 `xmax`에 남긴다.

더 이상 어떤 트랜잭션에서도 필요하지 않은 Tuple은 Dead Tuple이 된다. 일반 `VACUUM`은 이 공간을 같은 테이블에서 재사용할 수 있도록 정리한다.

```sql
VACUUM members;
```

하지만 일반 `VACUUM`은 보통 Relation 파일 자체를 축소해 운영체제에 공간을 반환하지 않는다.

```text
DELETE
└── Tuple을 더 이상 보이지 않게 표시

VACUUM
└── 해당 공간을 테이블 내부에서 재사용 가능하게 정리

VACUUM FULL
└── 테이블을 새로 작성해 파일 크기를 축소
```

`VACUUM FULL`은 테이블 전체를 다시 작성하고 `ACCESS EXCLUSIVE` Lock을 사용한다. 작업 중 다른 접근을 막을 수 있으므로 일상적인 정리 수단으로 사용해서는 안 된다.

Dead Tuple과 Vacuum 통계는 다음과 같이 확인한다.

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum
FROM pg_stat_user_tables
WHERE relname IN ('members', 'documents');
```

운영 환경에서는 Autovacuum을 끄기보다 테이블의 변경량과 크기에 맞게 설정을 조정하는 것이 일반적이다.

## 2.12 전체 흐름 정리

`UPDATE` 한 번이 처리되는 과정을 단순화하면 다음과 같다.

```text
1. 클라이언트가 UPDATE 실행
          │
          ▼
2. PostgreSQL이 대상 Tuple 확인
          │
          ▼
3. 기존 Tuple에 새 트랜잭션 정보 기록
          │
          ▼
4. 새로운 Tuple 버전 생성
          │
          ├── 조건 충족: 같은 Page에 HOT Update
          └── 조건 불충족: 일반 Update와 인덱스 갱신
          │
          ▼
5. 각 트랜잭션은 Snapshot에 맞는 버전을 조회
          │
          ▼
6. 이전 버전이 아무에게도 필요하지 않게 됨
          │
          ▼
7. Vacuum이 공간을 재사용 가능하게 정리
```

PostgreSQL의 저장 구조, MVCC, Vacuum은 서로 떨어진 기능이 아니다.

- Page와 Tuple 구조가 여러 행 버전의 저장 방식을 결정한다.
- 여러 Tuple 버전이 MVCC를 가능하게 한다.
- 사용이 끝난 Tuple이 쌓이기 때문에 Vacuum이 필요하다.
- Visibility Map은 Vacuum과 Index-Only Scan을 연결한다.
- Page의 빈 공간은 HOT Update 가능성에 영향을 준다.

## 2.13 정리

이번 장에서 살펴본 내용을 정리하면 다음과 같다.

- PostgreSQL의 일반 테이블은 Heap 형태로 저장된다.
- Relation 파일은 일반적으로 8KB Page로 나뉜다.
- Page 안에는 Header, Item Identifier, Free Space와 Tuple이 있다.
- `ctid`는 Tuple의 Page 번호와 Item Identifier 번호를 나타낸다.
- `UPDATE`는 기존 Tuple을 덮어쓰지 않고 새 Tuple 버전을 만든다.
- 조건이 맞으면 HOT Update로 인덱스 갱신을 줄일 수 있다.
- FSM은 Page의 여유 공간을, VM은 Page의 가시성 상태를 관리한다.
- 큰 가변 길이 값은 TOAST를 통해 압축되거나 별도 Table에 저장될 수 있다.
- 사용이 끝난 Tuple은 Vacuum이 재사용 가능한 공간으로 정리한다.

다음 장에서는 이 저장 구조를 바탕으로 Snapshot이 만들어지는 방식과 `Read Committed`, `Repeatable Read`, `Serializable` 격리 수준의 차이를 살펴본다.
