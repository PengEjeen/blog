## 앱이 늘어날수록 `nginx.conf`도 늘어났다

AI 코딩이 퍼지면서 새로 만든 앱을 올려 달라는 요청이 부쩍 늘었다. 처음에는 요청이 올 때마다 내가 도메인과 HTTPS를 설정하고, 앱에 맞는 `nginx.conf`를 작성했다. 설정 검증과 NGINX 리로드까지 마쳐야 제작자가 앱에 접속할 수 있었다.

한두 번은 할 만했다. 그런데 새 앱이 들어올 때마다 또 `nginx.conf`를 만들기가 싫어졌다. 앱을 만든 사람은 이미 배포할 준비를 마쳤는데, 주소를 받으려면 내가 설정할 때까지 기다려야 했다. 제작자가 앱을 만드는 속도가 빨라진 만큼, 등록 절차도 제작자가 직접 끝낼 수 있게 하고 싶었다.

## NGINX를 앞단에 두고 `/app/`부터 넘겼다

이미 운영 중인 서비스가 있어서, 먼저 NGINX 뒤에 Traefik을 붙였다. NGINX가 계속 외부 요청을 받고, 공용 도메인의 `/app/` 아래 요청을 Traefik으로 전달하도록 했다. Traefik은 Docker Provider로 각 앱 컨테이너의 라벨을 읽고, 요청 경로에 맞는 앱을 찾아 전달한다.

```text
공용 도메인의 /app/<앱 이름>
  → NGINX
  → Traefik
  → 해당 앱 컨테이너
```

이렇게 하니 기존 서비스가 쓰던 경로를 유지한 채 새 앱의 등록 방식부터 바꿀 수 있었다. 글을 쓰는 지금도 NGINX가 맨 앞단에 있다.

## 제작자에게는 앱 이름 하나만 맡겼다

공용 Docker Compose 예제를 만들어 제작자들에게 줬다. Traefik 라벨과 경로 규칙은 예제에 넣어 두었다. 제작자는 앱 이름 하나만 지정하고 올리면 됐다. 예를 들어 이름을 `notes`로 정하면 접속 경로는 `/app/notes`가 된다.

등록 방법을 설명할 때도 “이 예제에서 앱 이름만 바꾸면 돼요”라고 말할 수 있었다. 제작자들이 실제로 그 예제로 자기 앱을 알아서 올려 주기 시작했다. 고마웠고, 앱마다 프록시 설정을 손보던 일도 줄었다.

## 돌아보면 바뀐 건 등록을 끝내는 사람이었다

Traefik의 Docker 라벨 덕분에 앱을 배포하는 곳에서 라우팅도 함께 등록할 수 있었다. 공용 Compose 예제와 `/app/<앱 이름>` 규칙을 마련해 두니 제작자에게 프록시 설정 전체를 설명할 필요가 없었다. 다음에 비슷한 요청이 몰려도, 먼저 반복되는 작업에서 공통 설정을 뽑아내고 요청한 사람이 직접 마칠 수 있는지 살펴볼 것 같다.
